# MuseEcho PWA 前端优化设计

状态：已完成分节确认，待书面规格复核

日期：2026-08-23

## 1. 背景与目标

MuseEcho 已具备可工作的 React/Vite 分析前端、真实后端任务状态、共享音乐时间轴、响应式基础和可访问性测试。本轮优化不重写分析链路，而是在保持真实性、隐私边界和模型研发并行性的前提下，把现有网页演进为适合比赛现场展示与评委跨设备自助体验的可安装 PWA。

本轮目标：

1. 形成舒适、简约、具有比赛辨识度的浅色莫兰迪视觉系统；
2. 同等支持手机、平板和电脑，并适配 PWA 独立窗口；
3. 通过三级信息架构让首层只呈现核心功能，细节按需展开；
4. 使用克制、可降级的动效解释播放、选择、分析和导航状态；
5. 仅改动展示层与 PWA 包装，不阻塞后端模型、训练与评估工作。

成功标准：评委可以在 3–5 分钟桌面演示中理解核心能力，也可以在手机或平板上独立完成上传、等待、查看分析、展开和弦详情和返回上级页面。

## 2. 非目标与边界

本轮不改变：

- 后端 API 路由、请求或响应语义；
- Python 分析管线、模型结构、训练配置、数据集和评估流程；
- 真实数据、置信度、证据和保留期限的产品契约；
- 音频加密、访问控制、删除与过期行为；
- 用演示数据、前端计时器或预测文案替代真实后端状态。

前端可以在不改变 API 的前提下重组组件、路由语义、响应式布局、视觉令牌、交互动效和缓存展示。若实现中发现必须修改后端接口，应停止该项前端工作并另行设计，不把接口变更夹带进本计划。

## 3. 设计方向

采用“浅莫兰迪音乐工作室”。产品气质是安静、可信、可触摸的音乐分析工具：保留现有 Warm Editorial 的标题辨识度和证据导向，降低复古纸张感，增强应用界面的清晰度、稳定性和跨端操作效率。

用户应记住两个特征：

- 低饱和的暖灰、鼠尾草绿和陶土色界面；
- 一条贯穿播放器、进度和结构地图的“音乐呼吸线”。

不采用霓虹渐变、玻璃拟态、装饰性粒子、过度圆角、密集小卡片宫格或与音乐数据无关的漂浮元素。

## 4. 信息架构

### 4.1 一级功能

一级界面只保留四个核心入口：

1. 上传或继续分析；
2. 播放与歌曲概览；
3. 音乐结构地图；
4. 深入分析。

一级功能卡只显示功能名称、一个关键结论、必要状态和一个明确入口。格式限制、隐私细则、算法元数据与完整解释不占用首层主要空间。

### 4.2 二级功能

“深入分析”按真实能力分为节奏、调性、和弦、能量等二级页面。二级页面可以展示完整图表、时间筛选、置信度、文本摘要和进一步解释入口，但不能虚构当前后端尚未提供的结论。

### 4.3 三级详情

三级详情聚焦一个具体对象，例如单个和弦或选定时间片段。和弦详情展示符号、起止时间、置信度、组成音、音程和性质；证据不足时继续显示明确的未知状态。

前进、返回和关闭详情必须保留播放时间、当前选区、已选和弦、滚动位置和 React Query 中已有的分析结果，不因纯展示层导航重复请求数据。

## 5. 响应式应用壳

所有设备共享功能顺序和可访问名称，只改变导航和详情的空间呈现。

### 5.1 手机

- 使用单列主页面和底部导航；
- 结果可用后显示底部悬浮迷你播放器，持续暴露播放状态和当前时间；
- 二、三级功能使用全屏子页面；
- 标题栏提供明确返回按钮，并兼容浏览器历史和系统返回手势；
- 使用 `env(safe-area-inset-*)` 处理刘海屏和底部手势区；
- 虚拟键盘出现时不遮挡主要操作。

### 5.2 平板

- 使用八栏语义布局；
- 主内容和当前详情可以形成双栏；
- 播放器位于工作区顶部并保持易于触达；
- 竖屏空间不足时退化为手机式详情子页面，不压缩图表文字。

### 5.3 桌面与可调整窗口

- 使用最大宽度受控的十二栏布局；
- 左侧轻量导航、中间分析画布、右侧按需出现详情面板；
- 未选中具体对象时不保留空白详情栏；
- PWA 独立窗口缩窄时使用相同响应式规则，不假设固定桌面尺寸。

布局至少验证 390×844、768×1024、1440×900，并额外检查 320px 最小宽度和桌面窄窗口。任何尺寸不得产生页面级横向溢出。

## 6. 视觉系统

### 6.1 色彩令牌

| 角色 | 建议值 | 用途 |
| --- | --- | --- |
| 画布 | `#F4F2ED` | 全局暖灰背景 |
| 主表面 | `#FAF9F6` | 卡片、面板和应用栏 |
| 主文字 | `#30332F` | 标题和正文 |
| 次文字 | `#59615B` | 描述、帮助和辅助信息 |
| 主强调 | `#5D7162` | 鼠尾草绿主要操作和当前状态 |
| 和弦强调 | `#8F6658` | 陶土色和弦选择与理论信息 |
| 结构辅助 | `#71808A` | 雾蓝灰结构与时间信息 |
| 分隔线 | `#D9DCD5` | 边框、轨道和层级分隔 |

主强调与和弦强调在主表面上的对比度满足正文级 WCAG AA。最终实现继续为成功、警告、危险和未知状态保留独立语义令牌。颜色不能作为唯一编码；置信度、轨道和选择状态同时使用文字、形状、线型或图标差异。

### 6.2 字体与层级

- 品牌名和少量一级标题保留衬线字体，形成比赛辨识度；
- 导航、按钮、正文、数字和分析内容使用清晰的中文无衬线字体栈；
- 证据 ID、时间和算法元数据使用等宽字体；
- 活跃分析页不使用营销页式巨型标题，首屏优先展示歌曲、播放器和关键结论。

### 6.3 组件形态

- 卡片圆角为 12–16px，默认无阴影，以细边框和背景层次分区；
- 同一视口只保留一个主要强调操作；
- 核心功能使用宽卡片或功能条，不使用密集小方块宫格；
- 详情使用子页面、侧栏或抽屉，不继续向一级页面底部无限堆叠；
- 图标采用统一细线几何风格，并始终提供文字或可访问名称；
- 首页隐私规则与格式限制收纳为可展开的“上传说明”，上传授权仍须在提交前明确勾选。

## 7. 交互与动效

动效只服务于反馈、定位和数据关系。快速反馈目标为 120–150ms，常规状态变化为 240ms，分层进入最长不超过 320ms。优先使用 `transform` 和 `opacity`。

### 7.1 播放与拖动

- 拖动播放进度时，播放头轻微放大，附近波形柔和抬亮；
- 松手后显示一次细环扩散，并平滑定位到目标时间；
- 播放头、结构地图和当前时间共享同一时间状态，不创建第二套播放进度；
- 移动端拖动目标满足触摸尺寸要求，且不阻止页面必要的垂直滚动。

### 7.2 和弦选择

- 和弦块点击产生约 120ms 的轻压反馈；
- 选中时间段、播放头和详情标题使用同一陶土色联动；
- 组成音按短间隔依次淡入，强化“从符号展开到构成”的因果关系；
- 键盘选择获得相同状态结果，不依赖悬停。

### 7.3 页面和详情转换

- 手机前进时内容从右侧轻移进入，返回时反向退出；
- 平板和桌面优先展开详情栏，避免整页跳转；
- 返回后恢复原滚动位置、选区和焦点；
- 加载、错误或导航转换期间不隐藏系统级返回路径。

### 7.4 分析、加载和反馈

- 分析等待使用后端真实阶段驱动的分段轨道；
- 当前阶段缓慢呼吸，已完成阶段保留稳定节点，不伪造剩余时间；
- 读取结果时使用与真实内容结构一致的骨架屏；
- 等待时间较长时显示可读状态和重试操作；
- 成功反馈使用一次短促颜色扩散，不显示遮挡式庆祝动画；
- 错误区域淡入后保持静止，不抖动，并说明原因和下一步。

### 7.5 减少动态效果

在 `prefers-reduced-motion: reduce` 下，位移、扩散、逐项淡入和呼吸效果降级为即时透明度切换或静止状态。交互含义和状态提示不得因关闭动画而丢失。

## 8. 前端状态与数据流

现有上传、状态轮询、结果读取、时间线与删除流程继续作为单一事实源。展示层新增的状态限于：

- 当前一级/二级/三级视图；
- 当前详情是否展开；
- 当前安装提示、离线提示和版本更新提示；
- 恢复导航所需的非敏感 UI 状态。

`AnalysisResult`、`AnalysisStatus` 和现有 React Query 查询键保持稳定。播放器、结构地图和详情共同消费现有 timeline controller；和弦选择继续使用真实 `ChordResult`。纯界面导航不触发重复上传、重复分析或重复读取。

## 9. 错误、空状态与恢复

必须覆盖：

- 尚未选择文件；
- 文件预检失败和后端验证失败；
- queued、各分析阶段、complete、failed、expired 和 deleted；
- 结果读取失败、音频读取失败和重试；
- 和弦或调性证据不足；
- 在线、弱网和离线；
- PWA 更新可用、更新失败和恢复；
- 最近分析已过期、已删除或无权访问。

错误文案不暴露内部异常，不用顺滑文案掩盖不确定性。失败后只提供真实可执行的恢复动作。服务端确认过期、删除或不可访问后，前端立即清理对应的最近分析入口。

## 10. PWA 包装

### 10.1 安装与窗口

- 提供 Web App Manifest、应用名称、短名称、主题色、背景色和独立窗口模式；
- 提供适合 Android、iOS 和桌面的图标及 maskable 图标；
- 安装入口由用户主动触发，不在首次访问时强制弹窗；
- 不支持安装事件的 iOS 显示简短的“添加到主屏幕”说明；
- 启动时显示轻量品牌启动界面，再恢复可用的最近分析入口。

### 10.2 离线缓存边界

Service Worker 只缓存应用壳、字体、图标和必要静态资源。以下内容禁止进入离线缓存：

- 上传音频和解密音频响应；
- 分析结果、证据问答和访问凭证；
- 删除或过期分析的任何私有数据；
- API 错误响应中的敏感上下文。

离线时可以打开应用壳、查看使用说明和选择本地文件，但“开始分析”必须明确提示需要联网，不把任务伪装成已提交。

### 10.3 更新策略

检测到新版本时显示非阻塞提示，由用户确认后刷新。分析上传、删除确认或其他不可中断操作进行中时不得自动重载。刷新后使用稳定 URL 和查询缓存规则恢复可恢复的界面状态。

### 10.4 最近分析

本地只记录恢复入口所需的最小非敏感信息，例如分析 ID 和最后访问时间；不记录访问密钥、音频、分析正文或模型证据。若当前访问控制实际依赖不可安全持久化的凭证，则取消跨会话自动恢复，仅保留当前会话内恢复。

## 11. 可访问性与输入方式

- 保持 WCAG 2.1 AA 的适用对比度；
- 所有控件可通过键盘访问并具有可见焦点；
- 触摸目标建议不小于 44×44 CSS 像素；
- 图表提供文本摘要、当前时间、选中范围和事件列表替代路径；
- 焦点在打开详情时进入详情标题或首个有效控件，关闭后返回触发元素；
- 屏幕阅读器可以获知分析阶段、播放状态、选择变化、离线状态和更新提示；
- 横屏、缩放至 200% 和减少动态效果时仍能完成核心流程。

## 12. 实施阶段

### 阶段一：设计令牌与响应式应用壳

建立浅莫兰迪令牌、应用导航、断点、安全区域、基础动效和对应测试。保留现有 API 客户端和分析数据组件接口。

### 阶段二：核心流程渐进展开

精简上传首页，把格式和隐私说明收纳为辅助层；重组歌曲概览、结构地图和深入分析入口。

### 阶段三：详情与动态反馈

完成和弦详情的跨端呈现、播放器拖动反馈、页面转换、骨架屏和真实阶段进度表现。

### 阶段四：PWA 包装

加入 Manifest、图标、Service Worker、安装引导、离线壳、更新机制和安全缓存规则。

### 阶段五：比赛验收

完成跨设备、弱网/断网、刷新恢复、安装、更新、键盘、触摸和减少动态效果验证，并准备桌面演示与移动自助体验的统一演示路径。

## 13. 测试与验收

### 13.1 单元与组件测试

- 一级功能只暴露核心摘要，二、三级内容按交互显示；
- 前进、返回和关闭详情保留 timeline 与和弦选择；
- 上传授权、真实状态、未知状态、删除和错误行为不回归；
- 减少动态效果和离线提示按媒体查询与网络状态生效；
- PWA 更新提示不会在不可中断操作中触发刷新。

### 13.2 响应式 E2E

- 390×844、768×1024 和 1440×900 无横向溢出；
- 手机使用底部导航和全屏详情，平板支持双栏，桌面支持按需详情栏；
- 播放器和当前时间在结果浏览期间易于触达；
- 浏览器后退、应用内返回和直接 URL 恢复具有一致结果；
- 键盘可以选择和弦、调整时间范围、关闭详情并继续操作。

### 13.3 PWA 验收

- Manifest 字段、图标、独立窗口和安装路径有效；
- 离线打开应用壳成功，离线提交分析被明确阻止；
- Cache Storage 中不存在音频、分析响应、问答或访问凭证；
- 新版本提示可延后或确认更新，当前不可中断操作不会被自动刷新；
- Lighthouse PWA、可访问性和性能检查无阻断性问题。

### 13.4 回归边界

前端构建、类型检查、Vitest 与 Playwright 测试全部通过。Python、ML 和 API 测试不应因纯前端改造发生契约变化；若出现相关失败，视为越过隔离边界，不通过验收。

## 14. 首批实现范围

首批实现仅包括：

- 更新设计令牌和全局应用壳；
- 建立手机、平板、桌面导航骨架；
- 精简未上传状态的首页层级；
- 建立通用的功能入口与展开/返回模式；
- 为上述改动补充组件和响应式测试。

首批不实现所有深入分析页面、复杂播放器动效或完整 Service Worker。每个后续阶段都应建立在前一阶段已通过测试的可运行前端之上。
